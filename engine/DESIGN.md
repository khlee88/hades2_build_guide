# 추천 엔진 설계 (2-A, 페이블)

> 구현 대상: `engine/recommend.js` — **순수 함수 모듈**, 브라우저·Node 양쪽 동작, 외부 의존 없음.
> 입력은 `data/*.json`(1-C 확정본)과 런 상태. AI 호출 없음. 모든 숫자는 이 문서가 정본이며 `engine/weights.js`에 상수로 분리한다(2-C 튜닝용).

## 0. 한 줄 요약

**빌드 방향(`build_directions.json`)마다 현재 상태와의 적합도 F_d를 계산해 가중치 W_d로 만들고, 제시된 후보(신/은혜/망치)의 점수는 Σ W_d·fit(후보, d) + 방향 무관 항(생존·마력·융합·상충·항상 챙김)으로 낸다.** 이유 문장은 점수에 가장 크게 기여한 항에서 템플릿으로 생성한다.

---

## 1. 런 상태 (입력)

```jsonc
{
  "weapon": "staff", "aspect": "staff_melinoe",
  "region": 1,                       // 1~4 (지하 기준). UI가 관리
  "boons": ["zeus_heaven_strike"],   // 보유 은혜 id. 칸 점유/미점유/융합/전설 전부 여기
  "hammers": ["staff_cross_cataclysm"],
  "arcana": ["death", "the_furies"], // 런 시작 시 사용자 입력 (선택)
  "keepsake": "luckier_tooth",       // 현재 장착 기념품 (선택)
  "hex": null,                       // 비술 id (선택)
  "gods_seen": ["zeus"],             // 이번 밤 은혜를 받은 신, **받은 순서** (첫 신 판정에 사용)
  "hp_state": "mid",                 // "high" | "mid" | "low" — 사용자가 버튼으로 입력. 기본 "mid"
  "direction_lock": null             // 사용자가 방향을 고정하면 direction id
}
```

파생값(엔진 내부에서 계산, 저장하지 않음):
- `slotMap`: 5칸 → 점유 은혜 id 또는 null. `boons` 중 `occupies_slot`인 것으로 구성. **같은 칸에 2개가 오면 입력 오류** → 나중에 넣은 것만 남기고 경고.
- `owned`: `boons ∪ hammers` Set.
- `firstGod`: `gods_seen[0]` 또는 null.
- `slotBoonCount`: 점유 은혜 수 (수렴 단계 판정).

## 2. 방향 적합도 F_d 와 가중치 W_d

무기의 각 방향 d에 대해:

| 항 | 값 |
|---|---|
| 핵심 칸 s ∈ `core_slots`가 `slot_prefs[s]` 은혜로 채워짐 | 순위별 **+3 / +2.5 / +2 / +1.5**(4위 이하) |
| 비핵심 칸이 `slot_prefs[s]` 은혜로 채워짐 | 순위별 **+1.5 / +1.2 / +1 / +0.8** |
| `support_boons` 보유 | 개당 **+1.5** |
| `hammers` 보유 | 개당 **+2** |
| `requires_hammer` 보유 | **+4** |
| `requires_hammer`가 있는데 미보유 | **F_d = −∞ (비활성)**. 단 §6 망치 추천에서는 "방향 전환 열림" 보너스로 취급 |
| `avoid_boons` 보유 | 개당 **−2** |
| `aspect` ∈ `aspects` | **+2** |
| `firstGod` 기준 `first_god_map[firstGod]` 순위 | 1위 **+3**, 2위 **+1.5**, 3위 이하 **+0.5**, 목록에 없음 **0** |
| 난이도 | **−0.5 × (difficulty − 1)** |
| 기본값 | **+1** (모든 방향이 최소 1로 시작 → 초반엔 전부 열림) |

**수렴 단계** (`slotBoonCount` 기준):

| 단계 | 조건 | 활성 방향 |
|---|---|---|
| A 탐색 | 점유 은혜 0~1개 | 전부 |
| B 수렴 중 | 2~3개 | F_d 상위 3개 |
| C 확정 | 4개 이상 | 상위 2개 (메인, 보험) |

`direction_lock`이 있으면 단계 무시: 고정 방향 W=0.7, F_d 차상위 1개 W=0.3.

**가중치**: 활성 방향의 F_d를 0 이상으로 클램프한 뒤 합이 1이 되게 정규화. 비활성은 0.
메인 = W 최대 방향, 보험 = 2위. UI에는 W와 함께 방향명·난이도·요약을 보여준다.

## 3. 은혜 후보 점수 `scoreBoon(state, candidate)`

후보 입력: `{ id, rarity? }` — rarity ∈ `common|rare|epic|heroic|duo|legendary` (사용자 입력 선택, 기본 common).

### 3-1. 게임상 불가능한 후보 (선택지에 뜰 수 없으나 방어)
- 이미 보유 → 점수 −∞, 표시 "이미 보유".
- `conflicts` ∩ `owned` 중 **슬롯 유래가 아닌 것**(= 상대가 같은 칸 점유 은혜가 아닌 경우)이 있으면 → −∞, 표시 "상충: OO과 동시 불가".
- `prereq` 미충족(`cat:ring`은 `tags`에 `ring` 있는 보유 은혜, `cat:strike`는 보유 attack 칸 은혜로 해석) → −∞, 표시 "조건 미충족".
- 후보의 `aspect_only`/`aspect_excluded`(망치)도 동일 처리.

### 3-2. 방향 의존 항  `Σ_d W_d · fit(B, d)`

**칸 점유 은혜 B (slot = s)**
```
base(B,d) =
  B ∈ slot_prefs[d][s]           → 순위별 10 / 8 / 6 / 5 (4위 이하 5)
  s ∈ core_slots[d] (선호 아님)   → 2
  그 외 (비핵심 칸 채움)           → 3
```
칸 s가 이미 다른 신의 은혜 E로 채워져 있으면 **교체**:
```
fit = base(B,d) − base(E,d) − 2            // 교체 비용 2
```
교체 시 **융합 손실**: E가 어떤 융합 D의 요구 그룹을 **유일하게** 충족하고 있고 D가 아직 완성 전이면
- D ∈ `target_duos[d]` → **−4**, 그 외 융합 → **−2** (D마다).
- D가 이미 보유(완성)된 융합이면 게임상 융합이 사라지지 않으므로 손실 0. (1.0 기준 융합은 획득 후 유지 — 확인 필요 시 ISSUES)

**칸 미점유 은혜 B**
```
fit = B ∈ support_boons[d]  → 순위별 7 / 6 / 5 / 4
      B ∈ avoid_boons[d]    → −8   (숨기지 않고 "비추 (이유)"로 표시)
      그 외                  → 1
```

### 3-3. 방향 무관 항 (W와 무관하게 더함)

| 항 | 조건 | 값 | 배지 |
|---|---|---|---|
| 항상 챙김 | B ∈ `always_take.boons` | **+9** | `항상` |
| 생존 | `hp_state == low` **또는** (region ≥ 2 이고 보유 은혜에 `armor`/`heal`/`max_hp` 태그가 0개) | `survival_kit.passive` 순위별 **+4/+3.5/+3/+2.5**, `survival_kit.slot[s]` **+2** | `생존` |
| 마력 규칙 | 메인 방향 `omega_dependent` 이고 magick 칸 비어 있음 | B.slot == magick: region 1 **+2**, region ≥ 2 **+5** | `마력` |
| 융합 진전 | B가 아직 미충족인 융합 D의 요구 그룹을 충족 | D ∈ 메인/보험 `target_duos` **+2**, 그 외 **+1** (D마다, 최대 +6) | |
| 융합 완성 | B로 D의 모든 그룹이 충족됨 (다음에 D가 뜰 수 있음) | target **+5**, 그 외 **+2** | `융합 임박` |
| 융합/전설 후보 | rarity == duo | **12 + tier(S:4, A:2, B:0)**; legendary → **11** | `융합`/`전설` |
| 희귀도 | rare/epic/heroic | **+1 / +2 / +3** | |
| 신 풀 집중 | 신 풀 규칙 §5 | B.god ∈ gods_seen **+1**; 신규 신이고 풀이 (CAP−1) 이상 **−3** | `새 신` |
| 초보 안전 | `beginner_safe` 태그 | **+1** | |

### 3-4. 순위와 이유

- 점수 내림차순. 동점이면 (1) 배지 `융합 임박` > `생존` > `마력` (2) 빈 칸 채우기 > 교체 (3) id 사전순.
- **이유 1줄** (≤ 40자): 기여 항 중 절댓값 최대 1개를 템플릿으로. 교체·상충·비추는 항상 `warnings[]`에 추가.
- 출력:
```jsonc
{ "id": "...", "rank": 1, "score": 17.5,
  "reason": "메인 'Ω 공격 화력' 공격 칸 1순위",
  "warnings": ["서약 일격을 버리게 됨", "진행 중 융합 '파급 효과' 무효화"],
  "badges": ["메인", "융합 임박"],
  "breakdown": { "direction": 9.2, "survival": 0, ... } }  // 디버그·튜닝용, UI는 접어서 표시
```

**이유 템플릿** (우선순위 순으로 첫 매치):
1. 상충 → `"상충: {상대 name_ko}와 동시 불가"`
2. 융합 후보 → `"융합 은혜 — 무조건 최우선 (티어 {S/A/B})"`
3. 융합 완성 → `"'{duo name_ko}' 조건 완성 — 다음에 뜰 수 있음"`
4. 항상 챙김 → `"칸 안 차지, 조건 없이 이득"`
5. 회피 → `"비추: {avoid_reason 앞 30자}"`
6. 생존 → `"체력 관리용 — 지금 방어/회복이 없음"`
7. 마력 규칙 → `"Ω 빌드인데 마력 칸이 비었음"`
8. 방향 선호 (점유) → `"{메인|보험} '{d.name_ko}' {칸 한글} {순위}순위"`
9. 방향 보조 → `"'{d.name_ko}' 보조 {순위}순위"`
10. 교체 → `"{E.name_ko}보다 {d.name_ko}에 더 맞음"` (fit>0일 때만)
11. 기본 → `"빈 {칸 한글} 채움"` / `"무난함"`

칸 한글: attack=일반 공격, special=기술, cast=마법, sprint=질주, magick=마력.

## 4. 신 후보 점수 `scoreGod(state, godId)`

신 선택지(방 보상 문 위 심볼)는 어떤 은혜가 뜰지 모른다. **그 신이 줄 수 있는 은혜들의 기대값**으로 평가한다.

```
pool(G) = G의 은혜 중 §3-1 불가능 제외
top(G)  = pool(G)에서 scoreBoon 상위 3개 점수의 평균      // 현재 상태에서 그 신이 가장 잘 줄 수 있는 것
score(G) = top(G)
         + 융합 파트너: 메인/보험 target_duos 중 미완성 D에서, G의 은혜가 유일한 미충족 그룹을 채울 수 있으면 +4 (최대 +8)
         + 신 풀: G ∈ gods_seen +2 / 신규이고 |gods_seen| ≥ CAP−1 → −4
         + 첫 신 (gods_seen 비어 있음): first_god_map[G]의 1위 방향 difficulty가 1이면 +2, 방향 수 ≥ 2이면 +1
         + 기념품 일치: state.keepsake가 G의 god_favor면 +1 (이미 확정 등장이므로 정보 표시용)
```
헤르메스·아르테미스·카오스·셀레네가 선택지에 있으면: 헤르메스 = `always_take` 근거로 **top(G)** 그대로(보통 9~10점대). 셀레네: 비술 없으면 +8 고정("비술 확보"), 있으면 +3. 카오스: 초보는 +2 고정 + "저주 확인 후 결정" 문구. 아르테미스: top(G).

이유 템플릿: `"'{duo}' 마지막 조건을 채울 수 있음"` > `"메인 '{d}'의 {칸} 1순위 {boon}이 여기서 나옴"` > `"이미 은혜 받은 신 — 풀 집중"` > `"첫 신으로 무난 ({방향 수}개 방향 열림)"`.

## 5. 신 풀 규칙 (상수 `GOD_POOL_CAP`)

- 기본값 **4**. Hades 1의 규칙이며 Hades II도 "active god pool"(위키 왕의 강권 노트)이 존재. 정확한 상한은 미확인 → `weights.js`에 상수로 두고 ISSUES에 기록.
- 헤르메스·아르테미스·셀레네·카오스는 풀에 포함하지 않는다.
- 효과: `|gods_seen| ≥ CAP−1`이면 새 신에 감점(§3-3, §4). CAP 도달 후 새 신은 게임상 거의 안 뜨므로 감점 대신 표시만.

## 6. 망치 후보 점수 `scoreHammer(state, hammerId)`

```
불가능: aspect_only ≠ state.aspect / aspect ∈ aspect_excluded / conflicts ∩ owned ≠ ∅ → −∞ ("상충: {name_ko}와 동시 불가")
fit_d  = hammers[d] 순위별 10 / 8 / 6 / 5 / 4 (5위 이하 4), 목록 밖 1
score  = Σ W_d · fit_d
       + 방향 전환: 어떤 비활성 방향 d'의 requires_hammer == 후보 → +6, 배지 "방향 전환: {d'.name_ko}"
       + affects ∩ (메인 방향 core_slots ∪ 보유 은혜가 붙은 칸) ≠ ∅ → +2
       + beginner_priority: 1 → +3, 2 → +1, 3 → 0, 0 → −3
       + 후보의 conflicts에 **아직 안 가진** 같은 무기 망치가 있고 그 망치가 메인 방향 순위에 있으면 −1 (미래 선택지를 막음) — warnings에 "{name_ko}와 이후 동시 불가"
```
망치는 **교체가 아니라 누적**이므로 교체 페널티 없음. 선택 후 상태 갱신 → F_d 재계산(무브셋 변경 망치가 방향을 뒤집는 경로).

## 7. 런 시작 추천 `recommendRunStart(weapon, aspect)`

1. **아르카나**: `arcana_beginner_set.cards`를 이해도 상한(사용자 입력, 기본 10)까지 채우고, 남으면 `upgrade_path` 순서로 추가. `never_with` 쌍 위반 시 뒤 카드 제외. 방향별 `arcana` 힌트는 "이 무기면 이것도 고려" 문구로만.
2. **기념품**: `keepsake_plan.region1` 순서에서 사용자가 보유한 것 중 첫 번째 (보유 목록 없으면 전부 표시).
3. **비술**: `hex_beginner` 순서.
4. **열린 방향**: 무기의 모든 방향을 F_d(초기값: 기본 1 + aspect 보너스 − 난이도) 순으로, 각각 "핵심 칸 / 1순위 신 / 대표 융합 / 핵심 망치" 4줄 요약. 이 시점엔 신을 고정하지 않는다고 명시.

## 8. 다음 기념품 `recommendKeepsake(state)`

지역 클리어 후(기념품 교체 가능 시점) 호출.
1. 메인 방향 `target_duos` 중 **미충족 그룹이 정확히 1개**이고 그 그룹의 후보가 전부 한 신 G의 것 → G의 `god_favor` 기념품. 이유 `"'{duo}' 마지막 조건 — {G} 확정 등장"`.
2. 아니면 메인 방향의 **빈 핵심 칸** 1순위 은혜의 신 G가 `gods_seen`에 없으면 → G 기념품. 이유 `"{칸} 채울 {boon} 노림"`.
3. 다음이 보스 지역(region == 4)이면 `keepsake_plan.boss_region`.
4. `hp_state == low`면 `luckier_tooth`/`ghost_onion` 우선.
5. 그 외 현재 유지.

## 9. 방향 표시 `directionScores(state)`

활성 방향마다 `{ id, name_ko, weight, F, filled: [칸별 채움 여부], next_wants: 빈 핵심 칸 1순위 3개, duo_progress: [{duo, satisfied, total}] }`. 폰 UI 상단의 "지금 빌드" 카드가 이걸 그린다.

## 10. 모듈 계약

```js
// engine/recommend.js — CommonJS + 브라우저 전역 동시 지원
const Engine = createEngine(data /* {boons, duos, hammers, weapons, arcana, keepsakes, hexes, builds, gods} */, weights /* engine/weights.js */);
Engine.recommendRunStart(weapon, aspect, { graspCap, ownedKeepsakes })
Engine.recommendGods(state, offeredGodIds)          → [{id, rank, score, reason, badges}]
Engine.recommendBoons(state, offered /* [{id, rarity?}] */) → [{id, rank, score, reason, warnings, badges, breakdown}]
Engine.recommendHammers(state, offeredIds)          → 같은 형식
Engine.recommendKeepsake(state)                     → {id, reason}
Engine.directionScores(state)                       → [...]
Engine.applyChoice(state, {kind:'boon'|'hammer'|'god'|'keepsake'|'hex', id, rarity?}) → 새 state (불변, 슬롯 교체 자동 처리, gods_seen 갱신)
Engine.validateState(state)                         → [경고 문자열] (같은 칸 2개 등)
```
- 순수 함수. 난수 없음. 같은 입력 → 같은 출력 (테스트 전제).
- `weights.js`: 이 문서의 모든 숫자를 이름 붙인 상수로. 2-C에서 숫자만 바꿔 재실행.
- 에러는 throw 하지 않고 −∞ 점수 + 표시 문구로. 알 수 없는 id는 `validateState` 경고.

## 11. 1-C 열린 질문에 대한 결정

1. **수렴 속도**: 점유 은혜 2개부터 상위 3개, 4개부터 상위 2개(§2). 초보는 1지역 끝(보통 점유 2개)까지 열어두는 게 맞다고 판단.

## 12. 2-B 구현 시 주의 (오퍼스에게)

- `conflicts`는 슬롯 유래와 수동이 섞여 있다. **슬롯 유래 상충은 "교체"**(§3-2), **수동 상충은 "불가"**(§3-1). 구분법: 상대 은혜가 `occupies_slot`이고 같은 `slot`이면 슬롯 유래.
- `cat:ring`/`cat:strike` 토큰 해석을 잊지 말 것.
- 융합 `requires`의 그룹 충족 판정은 **현재 보유 은혜 기준**. 교체로 사라질 은혜는 제외하고 재계산해야 손실이 나온다.
- `first_god_map`에 없는 신(헤르메스 등)이 첫 신이면 F_d의 첫 신 항은 0.
- 점수는 부동소수. 출력 시 소수 1자리.
- SCENARIOS.md의 기대 결과는 **순위와 배지·경고의 존재**만 검사한다. 절대 점수는 검사하지 않는다(튜닝으로 바뀜).

## 13. 2-C 개정 (페이블) — TEST_RESULTS·프로브 검토 결과

구현이 설계대로 동작했으나 **설계 자체의 결함 2건**과 **구현 누락 1건**, 표현 문제가 나왔다. 아래가 정본이며 §3의 해당 항을 대체한다.

### 13-1. 융합 진전/완성/손실은 "도달 가능한" 융합만 센다 (설계 결함)
§3-3의 융합 진전은 "B가 미충족 그룹을 충족"이면 무조건 +1/+2였다. 그런데 어떤 신의 칸 점유 은혜든
그 신의 융합 8개 전부의 한쪽 그룹을 채우므로, **첫 은혜를 받는 순간 +6(cap)이 자동으로 붙는 허수**가 됐다
(S03 폭풍 고리 10.1점 중 6점). 손실도 같은 구조로 헤라 은혜 하나 교체에 −12가 찍혔다(S04).

정의: `reachable(D) = D ∈ target_duos(메인∪보험)  OR  D.gods ⊆ (gods_seen ∪ {후보의 신})`
- 진전·완성·교체 손실 모두 `reachable`한 융합만 대상.
- 후보의 신은 "지금 문을 골라 보고 있는 신"이므로 등장한 것으로 취급한다 (S05: gods_seen=[hestia]에서 제우스 은혜가 불벼락을 완성해야 함).

### 13-2. 회피(avoid)는 칸 점유 은혜에도 적용 (구현 누락)
`avoid_boons`에는 파도 일격·화산 일격처럼 칸 점유 은혜가 들어 있는데 구현은 미점유 분기에서만 검사했다.
쌍검 첫 신 헤파이스토스에서 화산 일격이 "빈 일반 공격 채움"으로 1위(P6). **회피면 교체 계산 전에 −8로 확정.**

### 13-3. 신 풀 항은 신 선택 단계에서만 (설계 결함)
은혜 선택 화면에 도달했다는 건 이미 그 신의 문을 고른 뒤다. 세 후보가 전부 같은 신이라 순위엔 영향이 없고
헤르메스·융합 후보와의 비교만 왜곡하며, "새 신" 배지는 혼란만 준다. → `FLAT.POOL_* = 0`. `GOD.POOL_*`은 유지.

### 13-4. 가중치
- `ALWAYS_TAKE` 9 → **7.5**: 헤르메스는 핵심 칸 1·2순위 채우기보다 아래, 3순위(6)와 비핵심 칸(3)보다 위.
  9였을 때 2순위 슬롯 은혜(8+1)와 동률이 되어 초보가 빌드 칸을 비워두고 헤르메스를 집는 쪽으로 밀렸다.

### 13-5. 이유 문장
- 전설 후보: `"전설 은혜 — 조건을 이미 채웠음, 최우선"` (기존엔 '무난함'으로 떨어짐)
- 교체인데 방향 점수 ≤ 0: `"{E}보다 나을 게 없음"` / `"{E}과 비슷한 급 — 바꿀 이유 부족"` — 1순위 은혜라도 후반에 2순위를 밀어내는 건 희귀도·석류 손실이 커서 권하지 않는다는 뜻을 순위 칭찬처럼 읽히지 않게(P5)
- 이유를 뽑는 방향은 **역할이 있는 방향 우선**(회피 > 선호/보조 > 미등재 > 중립), 같은 등급이면 가중치 큰 쪽. 보험 방향의 보조면 `"(보험 방향)"` 꼬리표
- 점유 은혜가 0개일 때 "메인" 대신 **"유력"**
- 완성 융합이 여럿이면 목표 → 티어 S>A>B 순으로 대표 하나 (S11: 강권이 아니라 불벼락이 나와야 함)
- 조사 자동 처리: 을/를, 과/와 (`대격변과`, `기예를`)
- 신 이름도 `nameOf`로 한글화 (`poseidon 확정 등장` → `포세이돈 확정 등장`)

### 13-6. 시나리오 추가 (S17~S22)
프로브를 회귀 테스트로 승격. SCENARIOS.md 참조.

### 13-7. 첫 신 보너스: "열리는 방향 중 하나라도 난이도 1" (설계 결함)
§4의 "first_god_map[G]의 **1위** 방향 난이도 1 → +2"는 map의 나열 순서에 결과가 좌우됐다. 지팡이에서 데메테르는
`[마법진 빌드(★2), Ω 공격 화력(★1)]`이라 +2를 못 받고 아프로디테가 역전(S02). 의도는 "초보에게 쉬운 길이 열리는가"이므로
**열리는 방향 중 하나라도 난이도 1이면 +2**로 고친다.

### 13-8. 융합 진전 단가·상한 인하
`DUO_PROGRESS_TARGET` 2 → **1.5**, `DUO_PROGRESS_CAP` 6 → **4**. 탐색 단계(A)에는 3방향의 목표 융합이 전부 대상이라
천상 일격 같은 관문 은혜가 +6을 받아 빈 마력 칸 채우기(마력 규칙)를 눌렀다(S18). 진전은 힌트이고, 빈 핵심 칸 채우기(5~10)를
넘어서면 안 된다. 결과: 지팡이 첫 은혜에서 **대전된 마력(마력) > 천상 일격 > 폭풍 고리** — Ω 의존 무기는 마력부터.

### 13-9. 이유 선택 규칙 정정
13-5의 "역할 있는 방향 우선"은 폐기. 보험 방향의 회피(−8×0.3)가 메인 방향의 보조 1순위(+7×0.7)를 덮어써 1위 후보에
'비추'가 붙는 모순이 생겼다(S06). **§3-4 원문대로 기여 절댓값 |W_d·fit| 최대 방향**에서 뽑고, 중립은 역할 있는 방향이 없을 때만.

## 14. 아르카나 추천 재설계 (4-A, 페이블) — 실플레이 피드백 반영

**피드백**: "무기를 바꿔도 아르카나가 안 바뀌고, 이해도 20인데 10짜리 세트만 준다."
**원인**: §7-1은 고정 세트 하나를 이해도 상한까지 자르는 것뿐이었다. 무기도, 각성 조건도 보지 않았다.

### 14-1. 사실 확정
- 이해도는 **1씩** 오른다 (10 → 30, 넋 소모, 후반 1당 350넋). UI의 5단위 세그먼트는 틀렸다 → 1단위 스텝퍼.
- 0 이해도 카드(달·켄타우로스·왕비·운명·신성·심판)는 **각성 조건**을 채우면 공짜로 켜진다. 조건은 6종뿐이므로 구조화해 판정한다 (`arcana[].awaken`).
- 커뮤니티 통념: 핵심 5~6장(죽음·퓨리 자매·불굴·마법사·고집 센 아들·전령)은 무기 공통. 이해도가 늘면 **Ω 의존 무기는 영겁·밤·밤그림자**, **마법 빌드는 퓨리 자매·전령**, **근접은 사냥꾼·연인** 쪽으로 갈린다. `build_directions.json`의 방향별 `arcana` 힌트가 이미 그 정보다.

### 14-2. 알고리즘 `recommendArcana(weapon, aspect, graspCap)` — 0/1 배낭 DP

> 초판은 탐욕 + "비용 효율(÷√이해도)"였고, 테스트에서 **죽음(4)이 싼 카드 3장에 밀려 빠졌다**(S01/S23). 초보에게 죽음 저항 1장은 1짜리 카드 셋보다 중요하다. 아래로 교체.

카드 가치:
```
value(c) = 핵심 목록(arcana_beginner_set.cards → upgrade_path) i번째 → CORE_BASE × CORE_DECAY^i   (1000, 500, 250, 125, 62, 31, 16, 8, 4, 2)
         | 그 외                       → PRIORITY[beginner_priority] (1→6, 2→3, 3→1; 0은 제외)
         + Σ_d DIRECTION_HIT × DIR_WEIGHTS[d 순위]      // 무기 방향 d의 arcana 힌트에 있으면
         + AWAKEN_LOOKAHEAD                              // '둘러싼 카드 중 하나' 조건(달)의 이웃이면
```
기하급수 덕에 **핵심 카드 하나가 비핵심 전부보다 크다** → 이해도가 얼마든 핵심이 먼저 채워지고, 남은 이해도에서 무기 방향 카드가 갈린다.
- 값이 결정되면 **0/1 배낭 DP**(후보 ≤ 25, 상한 ≤ 30)로 Σvalue 최대 조합을 구한다. 같은 값이면 이해도를 덜 쓰는 쪽.
- `never_with`(용력↔죽음) 둘 다 뽑히면 가치 낮은 쪽을 빼고 다시 푼다.
- 0 이해도 카드는 후보에 넣지 않고, 결과 집합의 **각성 고정점**으로 공짜로 붙인다.
- 출력: `cards`(태그 핵심/무기 방향/보조) · `awakened` · `free_cards`(잠긴 0 이해도 + 조건) · `next_up`(이해도 더 있으면 들어갈 2장) · `grasp_left`.

검증 결과(§S23/S24): 이해도 10 → 죽음·퓨리 자매·불굴·마법사·고집 센 아들(기존 세트와 동일). 이해도 20 → 무기별로 영겁/사냥꾼/밤 등이 갈리고 달·신성이 각성으로 붙는다.

### 14-3. 각성 조건 구조 (`data/arcana.json` `awaken`)
| 카드 | 위치 | type | 뜻 |
|---|---|---|---|
| 달 | [1,5] | `adjacent_any` | 둘러싼 카드(8방향) 중 하나 |
| 켄타우로스 | [3,3] | `one_each_cost` 1~5 | 비용 1·2·3·4·5 카드 각 1장 |
