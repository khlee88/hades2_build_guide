# 선택 로그 스키마 (`h2.log.v1` → `hades2_log_*.jsonl`)

> 목적: 나중에 **가중치를 데이터로 보정**하고 **추천 품질을 실측**하기 위한 기록.
> 2026-09-11 설계 합의, 구현 `app/src/patch_log.py`. 엔진·데이터는 건드리지 않는다.

## 어디에 쌓이나

GitHub Pages는 정적 호스팅이라 **받아주는 서버가 없다.** 그래서:

```
선택할 때마다  →  폰 브라우저 localStorage('h2.log.v1')에 누적   ← 자동
[파일로 저장]  →  누적분 전체를 .jsonl 파일로 덤프              ← 수동
```

- 브라우저는 **파일에 이어쓰기를 못 한다.** 버튼은 매번 "지금까지 전부"를 새 파일로 뽑는다
- 따라서 **가장 최근 파일 하나가 전체 스냅샷**이다. 이전 파일은 그것의 부분집합이라 버려도 된다
- 저장소에는 `data/runs/history.jsonl` **한 경로에 덮어쓰기**로 커밋한다. 이력은 git이 관리 → 중복 0
- 새로고침·탭 닫기·재부팅은 로그를 지우지 않는다. 지워지는 건 브라우저 사이트 데이터 삭제·시크릿 탭뿐

## 설계 원칙

1. **자동 기록, 버릴 수 있음.** "저장 버튼을 눌러야 남는다"로 하면 까먹었을 때 손실이다. 기본값이 보존이어야 한다
2. **이벤트 소싱(스냅샷 아님).** 변화만 적으면 재생으로 어느 시점 상태든 복원되고, **가중치를 바꾼 뒤 과거 런을 재채점**할 수 있다
3. **그때 화면에 뜬 점수·순위를 그대로 남긴다.** 재계산할 수 있는데도 남기는 이유 — 사용자는 *그때 본 순위*에 반응해 골랐다. 나중 값으로는 그 맥락이 복원되지 않는다
4. **제시된 것 전부를 남긴다.** 고른 것만 남기면 "3택 중 선택" 모델을 만들 수 없다

## 이벤트 4종 (JSONL, 한 줄 = 이벤트 1개)

공통 필드: `id`(런 id `YYMMDD-HHMM-xxxx`), `n`(런 내 순번), `t`(종류)

### `run` — 런 시작
```jsonc
{"t":"run","id":"260911-2143-7f3a","n":1,"ts":"2026-09-11 21:43:02",
 "w":"staff","asp":"staff_melinoe","grasp":20,
 "arc":["death","the_furies","persistence","the_sorceress","the_wayward_son"],
 "eng":"2026-09-11 21:40 KST","sv":1}
```
`eng` = 그때 엔진 빌드 스탬프(가중치 버전 판별용), `sv` = 스키마 버전

### `pick` — 선택 **(핵심)**
```jsonc
{"t":"pick","id":"260911-2143-7f3a","n":3,
 "kind":"boon",                                   // boon | hammer | god
 "rg":1,"hp":"mid","ns":0,                        // 지역 · 체력 · 채워진 칸 수
 "dir":[["staff_special",0.5],["staff_omega_attack",0.4]],   // 그때 방향 가중치 상위 2
 "off":[                                          // 제시된 것 전부 (비선택 포함)
   {"i":"zeus_heaven_strike","r":"rare","s":14.2,"k":1,
    "b":{"direction":9.2,"duo_progress":3,"rarity":1,"beginner":1}},
   {"i":"zeus_storm_ring","r":"common","s":8,"k":2,"b":{"direction":6.5,"duo_progress":1.5}},
   {"i":"zeus_ionic_gain","r":"common","s":6.5,"k":3,"b":{"direction":5.5,"beginner":1}}
 ],
 "c":"zeus_storm_ring"}                           // ← 라벨: 실제 선택
```
`i` id · `r` 희귀도 · `s` 점수 · `k` 앱이 매긴 순위 · `b` breakdown · `rep` 교체 여부(1)

> **`b`가 곧 조건부 로짓의 설계행렬이다.** 엔진이 이미 항목별로 계산해 두는 값이라
> 나중에 특징을 새로 만들 필요가 없다.

### 상태 변경
```jsonc
{"t":"hp","v":"low"}      {"t":"rg","v":3}        {"t":"keep","v":"vivid_sea"}
{"t":"hex","v":"hex_lunar_ray"}   {"t":"rm","v":"zeus_storm_ring"}   {"t":"undo"}
```
`undo`는 조작 실수 신호로도 쓸 수 있어 일부러 남긴다.

### `end` — 런 종료
```jsonc
{"t":"end","id":"260911-2143-7f3a","n":26,"ts":"2026-09-11 22:15:30",
 "route":"under","res":"died","rg":[1,1,0]}
```

| 필드 | 값 |
|---|---|
| `route` | `under`(지하·크로노스) / `surface`(지상·티폰) — **필수.** 없으면 "2지역"이 두 가지 뜻이 된다 |
| `res` | `clear` / `died` / `quit` |
| `rg` | 지역별 이진값. `[1,1,0]` = 1·2 클리어, 3에서 사망 · `[1,1,null]` = 3에서 **중단**(죽은 게 아님) · `[1,1,1,1]` = 완주 |

> 단조라서 "어디까지"만 고르면 `rg`가 결정된다. 그래서 입력은 탭 세 번(루트·결과·지역).
> **`end`가 없는 런**은 결과를 안 넣은 것 — 클리어율 통계에서는 빠지지만 **선택 학습에는 그대로 쓰인다.**

## 왜 지역별 이진값인가

`"3지역에서 죽음"`과 정보량은 **같다.** 이득은 모양에서 나온다:

| | |
|---|---|
| 라벨 수 4배 | 20런 = 결과 20개가 아니라 지역 라벨 80개 |
| 크레딧 할당이 좁아짐 | "25선택 → 클리어 1개"가 아니라 "2지역 진입 전 선택들 → 2지역 클리어" |
| 표준 모형에 맞음 | `P(지역 k 클리어 \| 지역 k 도달)` = 이산시간 위험모형. 적은 표본에 강하다 |

보스 도달 여부(`0`이어도 얼마나 근접했나)는 **일부러 안 넣었다** — 입력이 늘면 기록을 안 하게 되고,
안 쌓인 데이터가 정밀한 데이터보다 훨씬 나쁘다. 필요해지면 `sv`를 올려 추가한다.

## 이걸로 뽑을 수 있는 것

| 질문 | 방법 |
|---|---|
| **앱 1위를 실제로 얼마나 채택하나** | `c`가 `k==1`인 항목인 비율 → 추천 품질 단일 지표 |
| **"무난함"이 몇 %로 뜨나** | `b`가 `{direction:1}`뿐인 항목 비율 → 커버리지 구멍 실측 (목록 기준 추정은 38~48%) |
| 방향별 클리어율 | `dir` 1위 × `end.rg` |
| 무기·양상별 클리어율 / 지역별 사망 분포 | `run` × `end` |
| **가중치 학습** | `off[]` + `c` → 조건부 로짓 (특징 10개면 300~500선택 ≈ 15~20런) |
| **새 가중치로 과거 재채점** | 재생 (`eng`로 버전 확인) |

## UI

| 위치 | 기능 |
|---|---|
| **새 런 시작** 화면 상단 | 지난 런이 있으면 "지난 런 결과" 카드 — 루트 / 결과 / 지역 / ☐ 이 런은 기록하지 않기 |
| **관리 → 선택 기록** | `N런 · M선택 · KB` · [파일로 저장] [복사] · 런별 ✕ 삭제 · 기록 전체 지우기 |

- 파일명 `hades2_log_YYYYMMDD_HHMM.jsonl` (KST)
- 3.5MB 넘으면 관리 화면에 경고 (localStorage 한도 ~5MB, 런당 ~10KB → **약 400런**)
- 전체 지우기는 결과 미입력 런 수를 경고에 표시

## 주의

- **전체 지우기는 내보낸 뒤에.** 클리어를 쓰면 파일이 증분이 되어 "파일 하나 잃으면 그 런 소실"이 된다
- 여러 파일을 합쳐도 무해하다 — `id`+`n`이 있으므로 `sort -u`로 중복 제거된다
- 개인정보 없음(게임 선택 기록뿐). 저장소에 커밋해도 무방
